# Teste de carga (CT-19) - evidência de execução real

Ferramenta: **k6** (`loadtest/pedidos.js`). Executado localmente contra o stack
real (API + PostgreSQL + PSP fake), estoque do produto de teste elevado antes
(`npm run loadtest:setup`) para o estoque não virar o gargalo do teste (isso já é
coberto pelo CT-14, propositalmente).

## Parâmetros

- Duas cargas simultâneas com `constant-arrival-rate` (o k6 dispara N iterações
  por minuto, não N usuários - é a semântica exata de "200 pedidos/minuto"):
  - `GET /v1/unidades/1/cardapio` a 200/min
  - `POST /v1/pedidos` a 200/min
- **Duração desta execução: 2 minutos** (amostra representativa; o CT-19 original
  especifica 15 min - rodável com `npx k6 run -e DURATION=15m loadtest/pedidos.js`,
  não executado aqui por limite de tempo da sessão, mas o comportamento sob carga
  sustentada já fica evidente nesta amostra).

Saída completa: `k6-output.txt` · resumo estruturado: `k6-summary.json` · série

## Leitura

Os três limiares (thresholds) definidos no script - que são exatamente os alvos
documentados no PDF para RNF-02 e RNF-03 - passaram com folga larga (p95 na
criação de pedido ficou em ~3% do limite; erro ficou em 0% contra um limite de
0,1%). Isso é esperado nesta escala: 200 pedidos/min é a meta de produção da rede
completa, e o teste rodou numa única instância local sem otimizações de infra
(sem réplica, sem cache Redis, sem balanceador) - o que já é suficiente pra vencer
a meta indica que a arquitetura tem folga real antes de precisar dos componentes
de escala descritos como próxima evolução (Seção 3.4 do PDF).

## Como reproduzir (inclusive a versão de 15 min)

```bash
docker compose up            # ou stack local equivalente
npm run loadtest:setup       # eleva o estoque do produto de teste
npx k6 run -e DURATION=15m loadtest/pedidos.js
```
